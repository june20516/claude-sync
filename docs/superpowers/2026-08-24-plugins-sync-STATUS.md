읽기 실패와 0개의 구별.

**3.0.0 릴리즈에 포함하기로 결정했다**(2026-08-24). 스키마를 또 바꿔야 하므로

## 5. 반드시 알아야 할 것

**(1) "동기화하지 않는 키"를 로컬에서 지우면 안 된다.**
초판이 `normalize`에 키 제거를 넣었고, `normalize`는 로컬·레포·base 셋에 다 적용되므로
상태 기계가 그것을 **삭제**로 읽었다. 데이터 손실 경로 넷이 여기서 나왔다.
→ `held`(판정 보류)로 분리했다. **코어가 이제 이것을 집행한다** — `_normalized`가 키 집합
변화를 `ValueError`로 막는다.

**(2) `hold`는 두 축이다.** 값 보류(push 금지)와 행동 보류(CLI 명령 금지)는 다른 연산이다.
하나로 묶었더니 (1)과 **같은 형태의 실수**가 반복됐다. `diff`·`merge`·`next_base`는 **value
축만** 쓰고, `action_held`는 `restore_plan` 전용이다.

**(3) 값 보류 키는 base에서 제거한다.** "이전 base 유지"로 두면 보류가 풀리는 순간
얼어붙은 base로 케이스 3(삭제)이 난다.

**(4) 측정된 조건과 적용할 조건을 구별하라.** "배열은 install을 통과해도 보존된다"는
**이미 그 값을 가진 키**에 대한 측정이었다. 새 기기엔 키가 없으므로 `install`이 `true`를 쓴다.

**(5) 국소 수정은 잔재를 남긴다.** 3차 spec 리뷰 Critical 5건이 **전부** 2차 개정의 패치
잔재였다. 문서를 부분 수정할 때마다 용어·표·상호참조를 `grep`으로 전수하라.

**(6) 변조 확인 없이는 테스트를 믿지 마라 — 이번 실행의 가장 큰 교훈이다.**
Task 2~7에서 **매번** SURVIVE가 나왔다. 핵심 불변식(`next_base`의 값 동의 검사)을 지워도
414개가 전부 통과했고, `hold` 호출 계약은 세 함수 어디에도 고정되지 않았으며,
`BROKEN = None`으로 바꿔도 스위트가 조용했다. **전부 기존 테스트도 못 잡아 Task 8 게이트로는
영영 안 걸릴 것들이었다.** plan에 `Step 4b: 변조 확인`을 체크박스로 넣고, 훅 호출 계약 /
축 분리 / `{}` vs `None` 셋을 템플릿으로 못박은 이유다.

**(7) MCP가 검증하지 못하는 경로가 있다.** MCP는 `hold=no_hold`(두 축 항상 빈 집합),
`normalize=redact`(키를 안 지움)를 주입하므로, **보류 관련 결함과 `normalize` 계약 위반은
446개를 전부 통과한 뒤 `plugin_config`에서야 발현한다.** 그래서 코드 안에 훅 계약 주석을
박고, 소스 스캔 가드(`hold` 소비 함수 전수, `parse_backup` 호출 금지)를 넣었다.
