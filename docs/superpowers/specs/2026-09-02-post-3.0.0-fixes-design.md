## 1. 배경 — 무엇이 틀렸나

3.0.0을 올린 기기에서 처음 실제 `/sync-backup`을 돌린 결과를 뜯어본 것이 발견 다섯의 출처다. 백업 자체는 성공했다. 아래는 **그 결과물이 말하는 거짓과, 사용자를 파괴적 선택으로 이끄는 자리**다. 실측 근거는 전부 BACKLOG에 있다 — 여기서는 설계에 필요한 만큼만 되짚는다.

| # | 거짓 또는 결함 | 왜 생기나 |
|---|---|---|
| ① | 백업 4단계가 `reject`에 **"리모트가 앞선 변경이 있습니다"**를 단정한다. 실측된 `reject`(`agents/code-reviewer.md`)는 **로컬이 앞서** 있었다. 시키는 대로 restore에서 「백업 채택」을 고르면 로컬 41줄이 사라진다 | `reconcile_backup.py`가 **기준선 없음**(방향을 모름)과 **리모트가 앞섬**(기준선 있음)을 한 버킷 `reject`로 낸다 |
| ② | `in_sync` 파일의 기준선이 영영 생기지 않는다. 그래서 ①이 백업만 하는 기기에서 **계속** 재발하고, 나중에 레포만 바뀌어도 `fast_forward`가 아니라 충돌로 뜬다 | 10단계가 `push` 목록에 대해서만 `update_base.py`를 부른다. `in_sync`는 로컬 == 레포라 기준선을 공짜로 확정할 수 있는 유일한 경우인데 버린다 |

**이 기기의 지금 상태**(2026-09-02 실측): 임시 클론 `${TMPDIR}/claude-sync-repo`의 `mcp-servers.json`에 `claude.ai *` 7개가 그대로 있고, `~/.claude/.sync-state/base/`에는 `plugins.json`·`mcp-servers.json` 둘뿐 파일 기준선은 없다. **①②③④를 실기기에서 검증할 픽스처가 살아 있다.** BACKLOG의 "이 기기에서 지금 해야 할 것" 2번(커넥터 7개를 손으로 지운다)은 **하지 않는다** — ③이 그것을 없애야 할 대상이고, 지우면 ③의 실기기 검증 대상이 사라진다.

## 2. 목표 / 비목표

**목표.**

1. 백업이 **방향을 모르는 것**과 **리모트가 앞선 것**을 다른 문장으로 말하고, 어느 문장도 파괴적 선택을 가리키지 않는다.
2. 백업만 하는 기기에도 파일 기준선이 생긴다.
3. 표식의 `files` 맵이 **이 백업이 담은 것**을 적는다.
4. 어느 기기도 복원할 수 없는 MCP 항목을 백업이 **보여주고, 묻고, 지우고, 푸시한다.**
5. 레포 문서의 구문이 깨졌을 때 백업이 **마지막 정상 판본을 찾아 묻고 되돌린다.** 사용자는 git을 만지지 않는다.
6. `sync-config.json`의 `language` 하나로 사용자에게 보이는 문장의 언어가 바뀐다.
7. 복원 계획 JSON 둘이 같은 층 구조를 갖는다.

**비목표.**

- 백업 문서 스키마는 바뀌지 않는다. `SCHEMA_VERSION`(2)·`MIN_READER_VERSION`(3.0.0) 불변.
- `SKILL.md` 산문의 다국어화(BACKLOG 언어 ①의 2안). 산문은 한국어로 남는다.
- `collect_mcp.py`(backup)·`compare_mcp.py`(status)의 출력 층 변경 — 11장 「닫은 것」.
- restore·status가 레포를 수리하는 것 — 0장의 결정.
- 다운그레이드 **자동** 복구, `broken_syntax` **자동** 복구. 둘 다 묻는다.
- 2.x 기기를 막는 것. 여전히 불가능하다.

## 3. 설계 A — 기준선·표식 정합 (①②④)

### 3.1 `reconcile_backup.py`의 `reject`를 두 갈래로 가른다 (①)

이 레포의 보고 층 관례를 그대로 따른다 — `lib/report.py`의 `split_conflicts`(`repo_kept`/`repo_absent`)·`split_repo_ahead`(`present`/`absent`)처럼, 한 버킷을 **사용자가 할 일이 갈리는 사실**로 나눈다.

```json
{"push": ["..."],
 "in_sync": ["..."],
 "reject": {"remote_ahead": ["..."], "no_base": ["..."]}}
```

| 갈래 | 조건 (L 로컬 · R 레포 · S 기준선) | 4단계 문구 |
|---|---|---|
| `reject.remote_ahead` | S 있음, R ≠ S, L ≠ R | **지금 문구 그대로** — "리모트가 앞선 변경이 있습니다. 먼저 `/sync-restore` 하세요" |
| `reject.no_base` | S 없음, R 있음, L ≠ R | **새 문구** — "이 파일은 비교 기준선이 없어 어느 쪽이 앞선 것인지 판단할 수 없습니다. `/sync-restore`에서 양쪽을 보고 고르세요. **로컬 변경이 있다면 「백업 채택」은 그것을 버립니다.**" |

- `backup_action(local, repo, seen)`은 지금처럼 `in_sync | push | reject` 셋을 돌려준다(순수 판정, 기존 테스트 유지). `reject`의 갈래는 `seen_hash is None` 하나가 정하므로 `main()`이 그 사실로 가른다 — 갈래 함수를 따로 두어 두 판정이 어긋날 자리를 만들지 않는다.
- 이름 `no_base`는 `reconcile_restore.py`가 충돌 사유로 이미 쓰는 값(`{"reason": "no_base", "has_base": false}`)과 같다. 같은 사실에 같은 이름.
- 10단계 bash가 읽는 `push`는 모양이 바뀌지 않는다. `reject`를 읽는 프로덕션 소비자는 4단계 산문뿐이다(실측 — `grep reject`가 SKILL.md 4단계 한 줄과 테스트만 찾는다. plan의 Task가 전수를 다시 뜬다).
- 두 갈래 모두 그 파일을 push하지 않는다. 그것은 바뀌지 않는다.

### 3.2 10단계의 base 갱신 대상에 `in_sync`를 더한다 — 두 경로 모두 (②)

**BACKLOG는 "푸시 성공 게이트 안"만 말했다. 그것으로는 닫히지 않는다.** 실측 시나리오(`push` 비어 있음, 8개 `in_sync`, 1개 `reject`)에서 `plugins.json`·`mcp-servers.json`까지 변화가 없으면 10단계는 `git diff --cached --quiet`가 참인 **"변경사항이 없습니다" 경로**로 빠지고, 그 경로에는 파일 base 갱신이 아예 없다.

```bash
# reconcile 결과에서 push ∪ in_sync 를 한 번 뽑는다. 두 경로가 같은 목록을 쓴다.
mapfile -t BASE_RELS < <(python3 -c "
import json
data = json.load(open('/tmp/claude-sync-reconcile.json'))
for r in data.get('push', []) + data.get('in_sync', []):
    print(r)
")
if git diff --cached --quiet; then
  echo "변경사항이 없습니다. 모든 설정이 최신 상태입니다."
  REPO_HAS_CONTENT=1
  # in_sync 는 로컬 == 레포이므로 여기서도 base ← 로컬이 옳다.
  [ "${#BASE_RELS[@]}" -gt 0 ] && python3 "$SYNC_SCRIPTS/update_base.py" "$HOME/.claude" "${BASE_RELS[@]}"
elif git commit -m "..." && git push; then
  REPO_HAS_CONTENT=1
  [ "${#BASE_RELS[@]}" -gt 0 ] && python3 "$SYNC_SCRIPTS/update_base.py" "$HOME/.claude" "${BASE_RELS[@]}"
else
  echo "푸시에 실패했습니다. base를 갱신하지 않습니다."
fi
```

- `in_sync`는 L == R이므로 `update_base.py "$HOME/.claude"`(base ← 로컬)와 base ← 레포가 같은 바이트다. 기존 호출 형태를 그대로 쓴다.
- "변경사항이 없습니다" 경로에 `push`가 실려 있을 수는 없다 — `push`는 L ≠ R이거나 R 부재이므로 4단계의 복사가 트리를 바꾼다. 한 목록으로 두 경로를 부르는 것이 그래서 안전하다.
- **`reject`의 두 갈래는 어느 경로에서도 더하지 않는다.** `remote_ahead`는 로컬이 레포에 동의하지 않은 상태이고, `no_base`는 방향을 모르는 상태다. 어느 쪽도 "이 기기가 마지막으로 동의한 값"이 아니다.
- 11단계의 규칙 문장("push 성공 파일의 base ← 로컬 내용")을 "push 성공 파일 **과 in_sync 파일**의 base ← 로컬 내용"으로 고친다.
- **푸시 실패 경로는 그대로다.** 그 경로에서는 `in_sync`도 갱신하지 않는다 — 갱신해도 옳지만(레포가 안 바뀌었으니 L == R은 여전하다) "푸시 실패 = base 불변"이라는 한 줄 규칙을 지키는 쪽이 읽기 쉽다.

### 3.3 `generate_metadata.py`가 레포 작업 트리를 걷는다 (④)

**7단계 시점의 레포 작업 트리는 정의상 "이 백업이 담는 내용"이다.** 4단계가 `push` 복사와 `.syncignore` 삭제를 마쳤고, `reject` 파일은 옛 레포 판본 그대로이며, 다른 기기가 올린 파일은 거기 있다. `~/.claude`를 걷는 것은 "이 기기의 로컬"을 적는 것이지 "이 백업"을 적는 것이 아니다.

```bash
python3 "$SYNC_SCRIPTS/generate_metadata.py" "$SYNC_REPO/sync-metadata.json" "$SYNC_REPO"
```

- `build_metadata(tree_root, plugin_json_path)`. 둘째 인자는 **필수**다 — 기본값을 `~/.claude`로 두면 갱신되지 않은 호출자가 조용히 옛 동작으로 돌아간다(`shape_of`의 relpath를 필수로 둔 것과 같은 이유).
- 걷는 대상은 지금과 같다 — `agents/`·`skills/`·`CLAUDE.md`. `sync_state.iter_synced_relpaths(root)`가 정확히 그 집합을 root 하나로 yield하므로 **그것을 재사용**하고 이 스크립트의 자체 `collect`를 없앤다(plan이 확정). 끊어진 심볼릭 링크는 지금처럼 건너뛴다.
- **`.syncignore`를 읽지 않는다.** 4단계가 레포 트리에서 이미 지웠다. 소비자는 `check_status.py`·`reconcile_backup.py` 둘이 남는다 — 둘 다 `~/.claude`를 걷기 때문에 스스로 걸러야 하는 자리이고, 그 이유가 그대로 유효하다.
- `lib/syncignore.py` 모듈 docstring의 "**왜 여기 있는가**" 문단은 `generate_metadata.py`의 `~/.claude` 걷기를 근거로 적혀 있다. "규칙을 한 파일에 두는 이유"는 남기되(두 소비자 + bash `find`가 같은 규칙이어야 한다), 7단계를 근거로 든 문장은 "7단계는 레포 트리를 걷으므로 4단계의 삭제가 곧 표식의 제외다"로 바꾼다. **"backup — 제외한다"** 항목의 "7단계의 `sync-metadata.json`에도 이름·sha256을 남기지 않는다"는 **여전히 참**이다 — 근거만 필터에서 구조로 바뀐다.
- 가드의 뜻이 바뀐다. "표식이 제외 파일을 거른다"(필터 검사)에서 **"표식의 키 집합 == 그 트리의 동기화 대상 파일 집합"**(양방향 완전성)으로. 후자가 ④의 세 거짓(reject 해시·타 기기 파일 누락·제외 파일 유출)을 한 단정으로 덮는다.
- `written_by_version`·`min_reader_version`·`schema` 세 표식은 **바뀌지 않는다.** 바뀌는 것은 `files` 맵의 출처뿐이다.

**대안(채택하지 않음).** reconcile JSON을 넘겨 `reject` 파일만 레포 해시로 덮는다. 인자 둘과 reconcile 출력 형식에 대한 결합이 늘고, "다른 기기 파일 누락"은 그대로 남는다.

### 3.4 `/sync-status`의 같은 거짓 문장 — **추가 제안, 사용자 확인 필요**

`check_status.py`는 기준선 없는 파일을 `conflict` 버킷에 넣고 **"⚠ 충돌 — 양쪽 변경 (restore 시 해소 필요)"**로 찍는다. 아무도 양쪽을 바꾸지 않았을 수 있다 — ①과 같은 거짓이다. `sync-status/SKILL.md` 2단계는 이미 "아직 base가 없는 파일은 … 어느 쪽이 앞선 것인지 판단할 근거가 없기 때문"이라 적고 있어 **산문과 스크립트 출력이 갈린다.**

제안: `check_status.py`가 보고 시점에 `conflict`를 `S is None`으로 갈라 `no_base` 묶음을 따로 찍는다 — 머리말 "⚠ 기준선 없음 — 어느 쪽이 앞선지 알 수 없음 (restore 시 선택 필요)". `lib/sync_state.classify`는 **바꾸지 않는다**(`restore_action`의 완전성 단정과 소비자 둘이 걸려 있다). 3.1과 같은 사실을 같은 이름으로 가르는 것이고, 3장 안에서 가장 작은 변경이다. 세 스킬이 같은 사건에 같은 문장을 쓴다는 규칙(sync-backup 5단계 "세 스킬이 같은 케이스에 같은 동사를 쓴다")의 적용이기도 하다.

이 절은 승인된 설계 A에 없던 것이므로 사용자가 지우면 plan에서 뺀다.

## 4. 설계 B — 복원 불가 항목의 레포 정리 (③)

### 4.1 `mcp_config.unrestorable_reason(name, cfg)`

`restorable()`은 참·거짓만 돌려준다. 플러그인 어댑터의 `unrestorable_reason(section, key, value, repo)`과 같은 자리에 사유 함수를 둔다. 복원 가능하면 `None`.

| 갈래 | 사유 문장 (표시용 — 판정은 `restorable`이 한다) |
|---|---|
| 이름이 `VALID_NAME`(영숫자·하이픈·언더스코어)을 어긴다 | "이름 '…'이 `claude mcp add-json`의 이름 규칙(영숫자·하이픈·언더스코어)에 맞지 않는다" — `claude.ai Slack` 같은 계정 커넥터가 여기 걸린다 |
| config가 객체가 아니거나, `command`도 `url`+`type`(http/sse)도 없다 | "`command`도 `url`+`type`(http/sse)도 없어 등록 인자를 만들 수 없다 — 옛 v1 형식에서 승격된 항목이 이 형태다" |

- **불변식: `unrestorable_reason(n, c) is None ⟺ restorable(n, c)`.** 두 함수의 조건이 갈리면 양쪽 다 무증상이다(복원 가능한데 사유가 붙거나, 복원 불가인데 사유가 None이 되어 보고에서 빠진다). 테스트가 두 함수를 같은 픽스처로 돌려 동치를 건다 — 플러그인 쪽 `unrestorable_reason` docstring이 요구하는 것과 같다.
- 사유는 소비자 셋(status·backup·restore)이 **같은 함수**에서 받는다. 한쪽이 문장을 따로 쓰면 그것이 이 저장소가 결함 B라 부르는 형태(파서 두 벌)다.

### 4.2 세 스크립트의 출력

| 스크립트 | 더하는 키 | 집합 |
|---|---|---|
| `compare_mcp.py` (status) | `unrestorable`, `unrestorable_reasons` | `/sync-restore`가 새 항목으로 훑는 집합(`keyed_sync.route_new_keys`) 중 `restorable`이 거짓인 것. MCP에는 보류가 없어 `only_repo`와 같은 집합이지만 **플러그인과 같은 함수를 부른다** — 두 어댑터가 같은 자리에서 다른 집합을 보는 일을 만들지 않는다 |
| `collect_mcp.py` (backup) | `unrestorable`, `unrestorable_reasons` | **병합 결과** `servers` 중 **로컬에 없고** `restorable`이 거짓인 것 |
| `plan_mcp.py` (restore) | `unrestorable_reasons` (`unrestorable` 버킷은 이미 있다) | 버킷과 같은 키 집합. 7장의 층 통일 뒤에는 `sections["servers"]` 안 |

**backup이 `repo_ahead`가 아니라 병합 결과에서 뽑는 이유.** 기준선이 없으면 `merge`가 합집합으로 degrade하고, 그때 레포 전용 항목은 `repo_ahead`에 실리지 않는다(`keyed_sync.merge`의 `base is None` 갈래). 기준선이 있으면 그 항목은 매번 케이스 2로 `repo_ahead.absent`에 온다. 정리 제안은 두 경우 모두에 나가야 하므로 판정 입력을 `servers`로 잡는다. 판정은 "로컬에 없다"(이 기기 것이 아니다)와 "복원 불가"(어느 기기도 재현할 수 없다) 둘의 교집합이다.

**로컬에 있는 항목은 이름이 이상해도 목록에 넣지 않는다.** 그것은 사용자의 실제 설정이지 쓰레기가 아니다.

**문구가 바뀌는 자리.**

- backup 6단계 표의 `repo_ahead.absent` 행("다른 기기가 추가했습니다. `/sync-restore`가 이 기기에 설치합니다") — **`unrestorable`에 있는 이름에는 쓰지 않는다.** status의 `only_repo`/`unrestorable` 규칙(sync-status 2단계 "어느 목록에 실렸든 이 목록에 있으면 '복원할 수 없습니다'가 우선한다")을 backup에도 건다.
- status 2단계 MCP 절 — `only_repo` 중 `unrestorable`인 항목에 "어느 기기도 복원할 수 없는 항목입니다. `/sync-backup`이 레포에서 정리할지 묻습니다"를 쓴다. 사유를 그대로 보여주고 요약하지 않는다.
- restore 6-3 — 지금 문구 뒤에 "레포에서 정리하려면 `/sync-backup`이 제안합니다"를 덧붙이고 사유를 함께 보여준다.

### 4.3 `prune_mcp.py` — 레포에서 지우는 유일한 경로

새 스크립트 `skills/sync-backup/scripts/prune_mcp.py`.

```
prune_mcp.py <레포 경로> <이름> [<이름> ...]
```

- `mc.load_backup`으로 읽는다(구문 깨짐·미지 스키마는 기존 예외로 `report.skipped`에 접힌다 — 다른 스크립트 셋과 같은 `except` 튜플). 이름을 지우고 `mc.dump_backup`으로 쓴다(원자적).
- **거부 둘** — 잘못 배선된 이름을 조용히 지우지 않는다. 거부는 예외가 아니라 출력이다.
  - 로컬 `~/.claude.json`에 있는 이름 → `refused[name] = "로컬에 있는 서버는 지우지 않는다"`
  - `restorable`이 참인 이름 → `refused[name] = "복원 가능한 항목은 지우지 않는다"`
- 출력: `{"status": "ok", "pruned": [...], "not_found": [...], "refused": {name: reason}}`.
- **base·스테이징은 건드리지 않는다.** 지워지는 이름은 로컬에 없으므로 `next_base`에 애초에 실리지 않는다(`_next_base_normalized`: merged에 있고 local에 없으면 "동의 안 함" — 이전 base에 있을 때만 유지되는데, 로컬이 동의한 적 없는 이름은 base에 없다). 4.6이 그 사실을 고정점 테스트로 건다.
- 레포 파일 하나만 쓴다. 커밋·푸시는 10단계가 한다 — 별도 커밋을 만들지 않는다.

### 4.4 backup 6.5단계 「복원 불가 항목 정리」

6단계(MCP 수집) 뒤, 7단계(표식) 앞. 6단계 출력의 `unrestorable`이 비어 있으면 조용히 지나간다.

비어 있지 않으면 이름과 사유를 **전부** 보여주고 두 선택지를 준다. **목록 전체에 한 번 묻는다** — 항목마다 사용자가 할 일이 같다.

- **레포에서 정리한다** — `prune_mcp.py "$SYNC_REPO" <이름>...`을 실행한다. `refused`가 비어 있지 않으면 그 이름과 사유를 보여준다(지워지지 않았다). 10단계의 `git add -A`·커밋·푸시가 삭제를 함께 올린다.
- **이번엔 넘어간다** — 아무것도 하지 않는다. 다음 백업에 다시 묻는다.

물을 때 **반드시 함께 적는 것 둘.**

> "「복원 불가」는 **이 버전(3.1.0)이 아는 형식** 기준입니다. 상위 버전의 플러그인이 더한 형식이라면 그 기기에서 `/sync-backup`을 돌렸을 때 복원 가능한 값으로 돌아오니, 확신이 없으면 넘어가도 됩니다."
>
> "다른 기기가 이 서버를 실제로 쓰고 있다면, 그 기기의 다음 `/sync-restore`가 「다른 기기가 삭제했습니다」로 **묻고**, 「유지」를 고르면 그 기기의 진짜 설정으로 레포에 되돌아옵니다. 조용히 사라지지 않습니다."

첫 문장이 **조용한 자동 삭제를 하지 않는 이유**다(BACKLOG ③). `restorable()`의 지식은 버전에 묶여 있고(지금 아는 transport는 `command`와 `url`+`http`/`sse`뿐), 3.2.0이 새 transport를 더해도 `SCHEMA_VERSION`은 오르지 않으므로 3.1.0 기기가 그것을 "복원 불가"로 읽는다. **확인을 받는 것이 그 안전장치다.**

### 4.5 억제 — 다운그레이드가 의심되면 정리를 제안하지 않는다

4.5단계가 낸 `files["mcp-servers.json"].downgrade_suspected`가 참이고 사용자가 「복구하지 않고 계속한다」를 골랐으면, 레포는 v1 승격 항목투성이라 **전부** `unrestorable`로 뜬다. 그 자리에서 "전부 정리할까요?"가 나가면 안 된다 — 다른 기기가 실제로 쓰는 서버의 **이름**까지 지우게 되고, 복구 경로(4.4의 둘째 문장)는 있어도 사용자를 그리로 끌고 갈 이유가 없다.

규칙: **`downgrade_suspected`가 참이면 6.5단계는 목록을 보여주되 정리 선택지를 주지 않는다.** "먼저 4.5단계의 복구를 하세요"로 안내한다. restore 6-5의 `local_stale` 억제와 같은 모양이고, 그 문서 하나(`mcp-servers.json`)만 본다.

`collect_mcp`가 `skipped`이면 목록 자체가 없다 — 6.5단계는 돌지 않는다.

### 4.6 고정점 — 지운 뒤 두 번 더 백업해도 되살아나지 않는다

BACKLOG가 실측으로 확인한 것을 테스트로 건다.

1. 로컬 {a} · 레포 {a, 쓰레기 g} · base {a}(또는 None) → backup → `unrestorable == [g]`.
2. prune g → backup 2회 → 레포 = {a}, `repo_ahead`·`deleted`·`unrestorable` 전부 비어 있고, base = {a}. 2회차와 3회차가 바이트 동일.
3. **다른 기기가 g를 진짜로 갖고 있는 경우** — 그 기기 로컬 {a, g(진짜 값)} · base {a, g} → restore 계획에서 g가 `local_stale` → 「유지」(`keep_stale`) → backup → 레포 = {a, g(진짜 값)}, 그리고 g는 `restorable`이 참이라 `unrestorable`에 오지 않는다.

**"넘어간다"를 기억하지 않는다.** 영구히 남는 경우는 진짜 쓰레기뿐이다 — 3번이 보이듯 실제로 쓰는 서버라면 그 기기의 백업이 복원 가능한 값으로 바꿔 놓아 목록에서 사라진다. 기억을 두면 상태 파일이 하나 늘고(`plugins-held.json` 같은), 그것을 읽지 못하는 갈래가 또 하나 생긴다. YAGNI.

## 5. 설계 C — `broken_syntax` 복구를 플러그인이 한다 (⑤)

### 5.1 `detect_downgrade.py`가 구문 손상도 진단한다

파일별 항목에 **`broken_syntax`** 키를 더한다. `repo_shape == compat.SHAPE_BROKEN`이면 참. 그때도 `find_last_v2_commit`으로 후보를 찾는다 — 지금은 `downgrade_suspected`가 참일 때만 찾는다.

```json
"mcp-servers.json": {
  "status": "ok", "reason": null,
  "downgrade_suspected": false, "broken_syntax": true,
  "repo_shape": "broken", "base_shape": "v2_object",
  "candidate": {"sha": "...", "date": "...", "subject": "...", "entries": {"servers": ["..."]}},
  "newer_schema_seen": false
}
```

- `_skipped_file`도 같은 키를 갖는다(키 모양 동일 — 소비자가 `.get`으로 읽을 때 부재가 falsy로 접히는 것을 막는 기존 규칙).
- 두 갈래는 동시에 참일 수 없다 — `SHAPE_BROKEN`은 `_OLD_SHAPE`의 어느 값과도 다르므로 `downgrade_suspected`가 거짓이다(`compat.downgrade_suspected`가 `broken`을 `_SHAPES`의 한 값으로 알고 있어 예외 없이 거짓을 낸다 — 2026-09-02 실측).
- **후보 탐색을 재사용하는 근거.** `find_last_v2_commit`은 "v2이고 이 버전이 읽을 수 있는 마지막 커밋"을 찾는다. 깨진 문서에 필요한 것이 정확히 그것이다. 깨진 HEAD 커밋은 `shape_of == broken ≠ v2`로 건너뛰어지고, 손상이 작업 트리에만 있고 HEAD가 정상이면 HEAD가 후보가 된다 — 둘 다 옳은 복구 지점이다. 히스토리에 v2가 없으면(2.x 시절만 있다) `candidate`는 `null`이고 손으로 되돌리는 안내가 남는다.
- **스크립트 이름은 바꾸지 않는다.** 가드 수십 개가 `detect_downgrade.py`를 이름으로 부른다. docstring 첫 줄만 "레포 백업 문서 진단 — 다운그레이드 사고와 구문 손상"으로 고친다. 11장에 적는다.
- base는 판정에 쓰지 않는다. 구문 손상은 base 없이도 사실이다.

### 5.2 backup 4.5단계 — 한 루프에서 두 사고

절 제목을 "4.5 레포 문서 진단 — 다운그레이드·구문 손상"으로. `files` 항목마다 판정 순서:

1. `status == "skipped"` — 지금과 같다(그 문서의 `reason`을 알리고 계속).
2. **`broken_syntax`가 참** — "레포의 `<relpath>`가 JSON으로 읽히지 않습니다. 이 상태로는 이 문서의 백업이 건너뛰어집니다."
   - `candidate`가 있으면 sha·`date`·`subject`·`entries`의 버킷별 개수를 보여주고 **세 선택지**:
     - **복구한다** — `git -C "$SYNC_REPO" show "<sha>:<relpath>" > "$SYNC_REPO/<relpath>"` 후 계속한다. 5·6단계가 정상적으로 병합한다. (다운그레이드 복구와 같은 명령, 같은 "`<relpath>`는 지금 보고 있는 항목의 키다" 주의)
     - **복구하지 않고 계속한다** — 그 문서만 건너뛴다(5·6단계가 `broken_syntax`로 접는다).
     - **중단한다.**
   - `candidate`가 `null`이면 사고는 알리되 복구를 제안하지 않는다. **지금의 손으로 되돌리는 문구는 여기에만 남는다.**
   - `newer_schema_seen`이 참이면 후보가 그보다 오래된 것임을 명시한다(다운그레이드와 같은 규칙).
3. `downgrade_suspected`가 참 — 지금 4.5의 흐름 그대로.
4. 둘 다 거짓 — 조용히 지나간다.

**자동으로 복구하지 않는다.** 다운그레이드와 이유가 다르다 — 거기서는 "옛 기기가 의도적으로 지운 항목까지 되살리기 때문"이고, 여기서는 **손상 이후에 무슨 일이 있었는지 이 기기가 모르기 때문**이다(5.5).

### 5.3 다섯 곳의 문구 — 행위자를 플러그인으로

| 자리 | 지금 | 바꾸는 문구 |
|---|---|---|
| backup 5단계 · 6단계 | "그 파일을 정상 JSON으로 되돌린 뒤 다시 실행하도록 안내한다(레포 git 이력에 정상 판본이 있으면 그것으로 복구한다)" | "4.5단계에서 복구하지 않아 이 문서를 건너뜁니다. 복구하려면 `/sync-backup`을 다시 실행해 4.5단계에서 「복구한다」를 고르세요." **4.5단계에 후보가 없었던 경우에만** 지금 문구 |
| restore 5절 · 6절 | 같음 | "레포의 이 문서가 손상됐습니다(2.5단계 참조). **복구는 `/sync-backup`이** 마지막 정상 판본으로 되돌릴지 묻습니다 — restore는 레포에 쓰지 않습니다." |
| status 2단계 (플러그인·MCP 두 자리) | 같음 | "레포의 이 문서가 손상됐습니다(1.5단계 참조). `/sync-backup`이 복구를 제안합니다." |

**"그냥 지우라고 안내하지 않는다"는 다섯 곳 모두 그대로 둔다.** 그 경고의 근거(그 문서에만 있던 다른 기기의 항목은 이 기기의 로컬에 없어 다음 백업이 되밀 수 없다)는 바뀌지 않았다.

### 5.4 restore 2.5 · status 1.5의 진단 루프

두 스킬의 `files` 루프에 `broken_syntax` 갈래를 더한다. 다운그레이드 보고와 같은 문단 구조다.

> "백업 레포의 `<relpath>`가 JSON으로 읽히지 않습니다. 이 실행에서는 그 문서를 건너뜁니다(파일 동기화와 다른 문서는 그대로 진행합니다). **복구는 `/sync-backup`에서 합니다** — 마지막 정상 판본(`<sha>`, `<date>`)을 찾았으니 거기서 「복구한다」를 고르면 됩니다."

`candidate`가 `null`이면 "git 이력에 이 버전이 읽을 수 있는 정상 판본이 없습니다"까지 말한다. restore는 리모트에 push하지 않으므로 여기서 레포를 고칠 수 없다는 문장은 다운그레이드 절의 것을 그대로 쓴다.

### 5.5 복구 후의 병합은 안전하다

후보 판본은 그 문서가 마지막으로 정상이었던 커밋이다. 손상 이후에 다른 기기가 올린 내용이 있었다면 그것은 손상된 파일 안에 있었고 이미 읽을 수 없다 — 복구가 새로 잃는 것은 없다. 복구된 판본 위에 이 기기의 로컬이 3-way로 얹히고, 다른 기기는 자기 base와 대조해 자기 항목을 되민다(그 항목이 복구 판본에 없으면 그 기기에서 케이스 1로 다시 올라간다).

**그래도 묻는 이유.** 이 기기는 "손상 직전 커밋"과 "손상 커밋" 사이에 무슨 의도가 있었는지 모른다. 예를 들어 다른 기기가 서버 하나를 지우려다 쓰기가 잘렸다면, 복구는 그 삭제 의도를 되돌린다. 그 판단은 사용자 몫이다.

## 6. 설계 D-1 — 출력 언어 스위치

### 6.1 설정

`~/.claude/sync-config.json`에 **`"language"`** 키 하나. 값은 언어 이름이나 코드(`"en"`, `"English"`, `"ja"` …)이고 에이전트가 해석한다. 키가 없으면 한국어 — 지금 동작.

```json
{"repo_url": "git@github.com:user/claude-sync.git", "language": "en"}
```

### 6.2 규칙 — 세 `SKILL.md`의 1단계에 한 문단

> **`language`가 있으면 사용자에게 보이는 모든 문장을 그 언어로 낸다.** 이 문서의 인용문("> …")과 표의 안내 문구, 그리고 스크립트가 만든 문장(`message`·`reason`·`unrestorable_reasons`·`degraded_reason`·`base_staging_reason`)이 대상이다. **번역하지 않는 것**: 명령(`claude …`·`git …`), JSON 키와 버킷 이름(`repo_ahead`·`local_stale` …), 파일 경로, 서버·플러그인·마켓플레이스 이름, 판정 값. 스크립트 문장은 **내용을 바꾸지 않고 언어만** 바꾼다.

**"그대로 보여준다" 계약의 수정.** backup 2.5·restore 2.5의 "`message` 필드를 그대로 보여준다. 명령을 직접 타자하지 않는다 — 안내 문구는 `compat.py`가 만드는 것이 계약이고, SKILL.md가 따로 쓰면 드리프트한다"는 드리프트 방지 계약이다. 그 뜻을 보존한 채 이렇게 고친다.

> "`message`의 **내용**을 그대로 보여준다 — `language`가 있으면 문장만 그 언어로 옮기되, 안의 명령은 그대로 둔다. 명령을 직접 타자하지 않는다."

### 6.3 첫 실행

세 스킬 모두 설정 파일이 없으면 레포 URL을 묻는다. **그 질문에서 언어도 함께 묻는다.** 그 첫 질문 자체는 **사용자가 대화에 쓰는 언어**로 한다 — 영어 README를 읽고 온 사용자가 한국어 질문을 먼저 받는 것이 이 항목의 문제였다. 답을 `language`에 적는다. 한국어를 골랐으면 **키를 쓰지 않는다** — 부재가 곧 한국어이고, 같은 뜻의 표현을 둘 두지 않는다.

### 6.4 문서

`README.md`·`README.ko.md`에 설정 키(`repo_url`·`git_user_name`·`git_user_email`·`pull_only`)와 나란히 `language`를 적는다. 지금 README는 `pull_only`만 「Sync Behavior Model」에서 언급하고 설정 키 목록이 없다 — **설정 절을 하나 만들고** 다섯 키를 표로 둔다(둘 다). `backup-readme*.md`는 백업 레포 설명이라 해당 없다.

### 6.5 가드가 전부 산다

산문은 한국어로 남는다. `test_skill_wiring.py`·`test_restore_prose.py`·`test_user_docs.py`가 한국어 문자열을 바늘로 쓰는 것이 전부 그대로 유효하다. 더하는 가드: 세 스킬의 1단계에 `language` 규칙 문단이 있고 번역하지 않는 것의 목록이 같다는 것, README 두 벌이 `language`를 적는다는 것, 수정된 "그대로 보여준다" 문장이 두 스킬에서 같다는 것.

## 7. 설계 D-2 — `plan_mcp.py` 출력을 `sections` 층으로

### 7.1 범위는 restore 계획 하나

BACKLOG가 지목한 자리가 거기이고 혼동 경고 세 곳이 전부 `sync-restore/SKILL.md`에 있다(§5 버킷 표 머리말 "바로 뒤 6절의 MCP 표와 이름이 겹치지만 층도 처방도 다르다", 5-5 첫 문단 "바로 뒤 6단계의 MCP 표는 같은 이름들이 최상위인 계획", 그리고 §6 표). `collect_mcp`·`compare_mcp`는 11장에서 닫는다.

### 7.2 모양

```json
{"status": "ok",
 "sections": {
   "servers": {
     "add": [], "needs_secret": [], "unrestorable": [], "unrestorable_reasons": {},
     "in_sync": [], "local_ahead": [], "repo_ahead": [], "both_changed": [],
     "local_stale": [], "local_only": []}},
 "configs": {}, "secret_keys": {}}
```

- 섹션 이름은 리터럴이 아니라 `mc.SECTIONS`에서 뽑는다 — `detect_downgrade._mcp_buckets`와 같은 관례(언패킹으로 "섹션이 하나"라는 전제를 함께 건다). BACKLOG가 적은 `mcpServers`는 실제 상수(`"servers"`)와 다르므로 쓰지 않는다.
- **최상위에 남는 것: `status`·`configs`·`secret_keys`.** 플러그인 계획의 `install`·`config_keys`·`repo_values`·`local_values`가 최상위에 있는 것과 같은 층 — 실행 재료다. **섹션 안에 들어가는 것: 버킷 아홉과 `unrestorable_reasons`** — 판정이다. 플러그인 계획이 `unrestorable_reasons`를 섹션 안에 두는 것과 맞춘다.
- `mc.restore_plan`(어댑터)의 반환은 바뀌지 않는다. 감싸는 것은 `plan_mcp.build_plan`이다.
- `NEEDS_CONFIG` 버킷 읽기는 섹션 안에서 한다.
- `apply-base` 서브커맨드와 선택 JSON(`{"keep_stale": [], "keep_local": []}`)은 **바뀌지 않는다.**
- 마이그레이션은 없다 — `/tmp`에 쓰고 같은 세션이 곧바로 읽는 휘발성 JSON이고, 0단계가 스크립트와 SKILL.md를 같은 `SYNC_ROOT`로 고정하므로 버전이 다른 소비자가 없다(BACKLOG ②의 판정 그대로).

### 7.3 `sync-restore/SKILL.md`

- §6 전체를 새 층으로 다시 쓴다. 6-1~6-6의 처방은 바뀌지 않는다 — 읽는 자리만 `sections["servers"]` 안이 된다.
- 경고 세 곳을 **한 문장**으로 줄인다: "두 계획은 같은 층 구조다 — 버킷은 `sections[<섹션>]` 안, 실행 재료는 최상위. 섹션이 플러그인은 셋, MCP는 하나(`servers`)다."
- 6-4의 "1. 그 이름이 unrestorable 목록에 있으면 채택 선택지를 제시하지 않는다"는 그대로다.

### 10.2 실기기 스모크 — 이 기기가 픽스처다

**순서가 중요하다.** ①②③④의 픽스처가 한 번의 `/sync-backup`으로 소비된다.

1. **3.1.0 설치 전에** `/sync-status`를 한 번 돌려 지금 보고를 남긴다(대조군).
2. 3.1.0 설치·재시작 후 **`/sync-backup`** 한 번:
   - 4단계: `reject.no_base == ["agents/code-reviewer.md"]`, 새 문구가 나가고 "리모트가 앞선"이 나가지 않는다 (①)
   - 6.5단계: `claude.ai *` 7개가 사유와 함께 뜨고, 「정리한다」 → `prune_mcp` 출력의 `pruned`가 7개, `refused` 비어 있음 (③)
   - 10단계: "변경사항이 없습니다"가 **아니라** 커밋 경로(프룬이 트리를 바꿨다) → `~/.claude/.sync-state/base/`에 `in_sync` 8개의 파일 기준선이 생긴다. `agents/code-reviewer.md`의 기준선은 **없다** (②)
   - 레포의 `sync-metadata.json`에서 `agents/code-reviewer.md`의 해시가 레포 판본(`1be61088…`)이고, 이 기기에 없는 다른 기기 파일이 있으면 그것도 맵에 있다 (④)
3. **`/sync-backup` 한 번 더** — `unrestorable` 비어 있음, `repo_ahead`·`deleted` 비어 있음, "변경사항이 없습니다" 경로, 파일 기준선 8개 불변 (③ 고정점, ② 두 번째 경로)
4. **`/sync-restore`** — 계획 JSON이 `sections["servers"]` 층이다 (7). `agents/code-reviewer.md`가 충돌로 뜨면 **「로컬 유지」**를 고른다(BACKLOG "이 기기에서 지금 해야 할 것" 1번 — 「백업 채택」은 41줄을 버린다). 그 뒤 `/sync-backup`이 그 파일을 `push`로 올리고 기준선이 생긴다.
5. `sync-config.json`에 `"language": "en"`을 넣고 **`/sync-status`** — 문장은 영어, 명령·키·이름은 그대로 (6).
6. ⑤는 실기기 레포를 깨뜨리지 않는다. 임시 클론을 복제한 **버리는 레포**에서 `mcp-servers.json`을 잘라 4.5단계의 세 선택지를 한 번씩 돈다.

### 10.3 변조 — plan이 task마다 다섯 축을 세운다

plan ③의 템플릿(훅 호출 계약 · 축 분리 · `{}` vs `None` · I/O 층 · 입력 축)을 그대로 쓴다. 이 spec에서 특히 위험한 자리:

- **축 분리**: `reject.remote_ahead`와 `reject.no_base`를 맞바꾸기 · `broken_syntax`와 `downgrade_suspected`를 맞바꾸기 · `refused`의 두 사유를 맞바꾸기
- **입력 축**: 10.1의 "기준선 없음·있음 두 갈래" 픽스처에서 한 갈래를 빼기 · 고정점 회차를 줄이기 · `unrestorable_reason` 동치 픽스처에서 정상 케이스를 빼기(그러면 "항상 사유가 있다"로도 초록이다)
- **`{}` vs `None`**: `prune_mcp`의 `not_found`를 `pruned`로 · 후보 없음을 `broken_syntax: false`로

명세는 `docs/superpowers/mutations/plan4-task-NN.json`에 남긴다(plan ③의 corpus 규칙).

## 12. 오픈 이슈 (plan에서 확정)

1. **3.4의 채택 여부** — 사용자가 spec 검토에서 정한다. 채택하면 `check_status.py`의 머리말 문구와 status 3단계 어휘 한 줄이 늘고, `test_reconcile.py`의 `section_of` 픽스처에 갈래 하나가 는다.
2. `generate_metadata.py`가 `iter_synced_relpaths`를 재사용할 때 끊어진 심볼릭 링크 처리가 지금과 같은지(`os.walk`는 링크 파일을 yield하고 `file_sha256`이 `FileNotFoundError`로 건너뛴다) — plan Task가 기존 테스트 `test_dangling_symlink_is_skipped_not_fatal`로 확인한다.
3. 6.5단계가 `orphaned` 보고(5단계 최상위)와 같은 자리에 놓이는지, 12단계 결과 보고에 "정리한 항목"을 어떤 형태로 싣는지 — plan이 정한다.
4. `prune_mcp.py` 호출줄이 `test_script_root.py`(SKILL.md를 **실행해서** 재는 쪽)에도 앵커를 요구하는지 — plan Task가 실측한다.
5. 언어 규칙 문단의 정확한 문장과 "번역하지 않는 것" 목록의 가드 형태(세 스킬에서 같은 목록을 뽑아 대조) — plan이 정한다.
6. 릴리즈 노트의 영어판 필요 여부 — 3.0.0은 한국어 하나였다. 언어 스위치가 들어가는 릴리즈이므로 영어판을 함께 내는 것이 자연스럽지만, 사용자가 정한다.
