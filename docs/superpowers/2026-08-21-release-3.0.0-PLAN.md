# 3.0.0 릴리즈 계획

- 작성: 2026-08-21
- 릴리즈 브랜치: **`release/3.0.0`** (`main`의 `67ab092`에서 분기)
- 상태: 두 작업 중 **2/2 완료** — 배포 절차(4장)로 진행 가능

`main`에는 아직 아무것도 머지하지 않는다. 3.0.0에 실릴 작업이 전부 `release/3.0.0`에
모인 뒤에 한꺼번에 `main`으로 보내고 배포한다.

---

## 1. 왜 릴리즈 브랜치인가

3.0.0은 **역호환이 없는 릴리즈**다. `mcp-servers.json`의 스키마가 v1 배열에서 v2 객체로
바뀌고, 구버전 기기가 이 백업을 만나면 `/sync-status`가 죽거나 `/sync-backup`이 파일을
파괴한다(자세한 것은 `2026-08-21-version-compat-BRIEF.md` 1장).

그래서 **"버전 호환성 대처"까지 함께 실어야 릴리즈로서 완결된다.** MCP 재설계만 먼저
`main`에 올려 배포하면, 사용자는 호환성 안내도 차단 장치도 없는 상태에서 major 전환을
겪게 된다. 두 작업을 한 릴리즈로 묶는 이유다.

### 작업 2 — 완료 내용

`specs/2026-08-21-version-compat-design.md`(설계), `plans/2026-08-21-version-compat.md`(구현 계획),
`2026-08-21-version-compat-BRIEF.md`(조사 기록) 참조. 요약:

- **실측 확정**: `autoUpdate`는 마켓플레이스와 **설치된 플러그인을 모두** 갱신한다(사용자 조작
  없이 `figma` 2.2.95 → 2.2.96이 올라간 것을 관찰). 그런데도 불일치 창은 닫히지 않는다 —
  서드파티 마켓플레이스의 기본값이 꺼짐이고 `settings.json`은 동기화 대상이 아니라 전파되지
  않으며, 갱신은 세션 시작 후 0~10분 랜덤 지연 뒤에만 일어나고, 갱신돼도 그 세션은 옛 코드를 쓴다.
- **(a) 표식**: `sync-metadata.json`에 `written_by_version`·`min_reader_version`·`schema`.
  `min_reader_version`은 현재 버전이 아니라 major에 묶인 상수이고, 그 불변식을 테스트가 강제한다.
- **(b) 가드**: `lib/compat.py` 하나가 판정과 안내 문구를 모두 만든다. backup만 차단,
  status는 경고만, restore는 질문. 차단이어도 종료 코드는 0이다(그래야 안내가 보인다).
- **(c) 탐지·복구**: `detect_downgrade.py`가 git 히스토리에서 마지막 정상 백업을 찾아 제안한다.
  자동 복구는 하지 않는다.
- **함께 고친 것**: 세 SKILL.md의 0단계가 `find | head -1`로 임의 버전의 스크립트를 골랐다.
  `plugins/cache` 한정 + semver 필터 + 버전 성분 정렬로 교체했다. 이것 없이는 3.0.0 세션이
  2.0.0의 `generate_metadata.py`를 실행해 표식이 조용히 안 써진다.
- **불변식 둘 추가**: 판정 불가를 통과로 접지 않는다(6), 테스트는 의미 역전을 잡아야 한다(7).
  `2026-08-20-mcp-redesign-STATUS.md` 5장 참조.
- 테스트 166 → **367 passed**

## 3. 남은 일

**작업 2까지 끝났다. 남은 것은 아래 4장의 배포 절차뿐이다.**

`feat/version-compat`을 `release/3.0.0`으로 PR(**target이 `main`이 아니다**)한 뒤,
`release/3.0.0`을 `main`으로 보낸다.

### 지켜야 할 것

- **버전을 올리지 않는다.** `plugin.json`·`.claude-plugin/marketplace.json`은 이미 `3.0.0`이다.
- **이 개발 기기에서 `/sync-backup`을 실행하지 않는다.** 캐시가 아직 `2.0.0`이라 백업 레포가
  파괴된다. 플러그인을 올리고 재시작한 뒤에만 실행한다.

## 4. 배포 절차 (작업 2 완료 후)

**푸시·배포는 외부 동작이므로 사용자 승인을 받고 실행한다.**

```bash
# 1) 릴리즈 브랜치에서 최종 검증
git checkout release/3.0.0 && git pull
uv run --with pytest pytest plugins/claude-sync/tests -q

# 2) 버전 일치 확인 (둘 다 3.0.0이어야 한다)
grep -rn '"version"' .claude-plugin/marketplace.json plugins/claude-sync/.claude-plugin/plugin.json

# 3) main으로 PR
gh pr create --base main --head release/3.0.0 --title "release: 3.0.0"
```

머지 후:

```bash
claude plugin marketplace update claude-sync
claude plugin update claude-sync     # restart required to apply
claude plugin list | grep -A2 claude-sync   # 3.0.0인지 확인
```

### 배포 순서 — 반드시 지킬 것

> **모든 기기를 3.0.0으로 올린 뒤에 어느 기기에서든 `/sync-backup`을 실행한다.**

v2.x 기기의 백업 단계는 레포 파일을 읽지 않고 `mcp-servers.json`을 통째로 재생성하므로,
한 번만 실행해도 v3 파일이 옛 배열 형식으로 되돌아가고 **명령에 공백이 든 서버가 누락된다.**
이번 전환에서 이것을 막는 확실한 방법은 실행 순서뿐이다 — 옛 버전에는 우리가 가드를 넣을 수
없기 때문이다.

**현재 이 개발 기기의 캐시는 `claude-sync/2.0.0`이다.** 즉 지금 이 기기가 바로 그
"낮은 버전 단말"이므로, 플러그인을 업데이트하기 전에는 `/sync-backup`을 실행하지 않는다.

### 태그

`claude plugin tag`가 `{name}--v{version}` 규약을 제공한다. 릴리즈 커밋에 남기려면:

```bash
claude plugin tag plugins/claude-sync --dry-run     # 먼저 확인
claude plugin tag plugins/claude-sync --push
```

`plugin.json`과 marketplace entry의 버전이 일치하는지 검증해 주므로 수동 태깅보다 안전하다.

## 5. 이 릴리즈에 싣지 않는 것

후속 과제로 등록되어 있으며 3.0.0의 범위가 아니다.

| 과제 | 문서 |
|---|---|
| `plugins.json`의 동일 결함 (통째 덮어쓰기, 켬/끔 미감지, 예외 처리 부재) | `2026-08-20-plugins-sync-followup-BRIEF.md` |
| 공용 키 단위 3-way 코어 추출 (`mcp_config` → 어댑터화) | 같은 문서 5장 |

`plugins.json` 작업의 **첫 task는 스키마 설계가 아니라 `extract_plugins.py`가 파괴하지
않게 만드는 것**이다. 쓰기가 wholesale인 한 스키마를 어떻게 설계하든 파괴된다.
